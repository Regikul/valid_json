# Контракт с core

Этот слой строит типы, определённые в [validator-core](validator-core.md), и не переопределяет их. Результат компиляции — полное транзитивное замыкание resources: все nodes и ссылки готовы, сетевых и registry lookup на пути `validate/3` нет. Runtime хранит `compiled()` как непрозрачное значение.

Непрозрачность означает и локальность узлу: `compiled()` содержит `re:mp()`, который действителен только там, где скомпилирован. Артефакт нельзя перенести на другой узел и нельзя сохранить между запусками — переносимы и кэшируемы только исходные документы, а компилирует каждый узел для себя.

Resources участвует в JSON Schema conformance; runtime ownership — библиотечная эксплуатационная надстройка и официальным suite не проверяется.

# Schema resources

Schema resource — схема с каноническим абсолютным URI ([core.txt:547](../references/json-schema/draft-2020-12/core.txt)). Корень документа и каждая признанная подсхема с `$id` образуют отдельные resources; исключение — fragment-only `$id` в Draft 6/7: он объявляет named target текущего resource. Resource является общей областью:

| Область | Данные в `#resource{}` |
| --- | --- |
| base URI и абсолютные локации | `id` |
| dialect | `dialect` |
| статические и динамические anchors | `anchors`, `dynamic_anchors` |
| Draft 2019-09 recursive scope | `recursive_anchor` |
| JSON Pointer space | `nodes` |

Встроенный resource без `$schema` наследует dialect объемлющего ([core.txt:2122](../references/json-schema/draft-2020-12/core.txt)). В Draft 2020-12 это нормативно; для Draft 2019-09 это выбранное implementation-defined поведение. Resource с собственным `$schema` может сменить dialect в Draft 2019-09/2020-12; Draft 6/7 допускают `$schema` только у корня документа. Указатели внутри нового resource считаются заново от его корня, поэтому синтаксический путь в документе не используется как `pointer()`.

Компилятор посещает только schema positions, заданные активными applicator keywords или `$defs`. `$id` внутри неизвестного значения не создаёт resource; ссылка в такое место завершается `non_schema_target`. Это сохраняет требуемое поведение `optional/unknownKeyword`; несовместимый `optional/refOfUnknownKeyword` находится вне профиля как undefined behavior.

# Registry без сети

Документы регистрируются до компиляции. `$ref` и `$schema` читают один реестр; незарегистрированный URI — compile error. Conformance remotes кладутся под `http://localhost:1234/...`, без resolver callback или download; URI не означает обязательной сетевой загрузки ([core.txt:1826](../references/json-schema/draft-2020-12/core.txt)). Метасхемы четырёх канонических диалектов в `store()` не лежат и описаны во [встроенной области](#встроенные-метасхемы).

```erlang
-record(document, {
    registered :: uri(),
    canonical  :: uri(),
    json       :: json()
}).

-record(store, {
    base      :: uri() | anonymous,
    documents :: #{uri() => #document{}}
}).

-type store() :: #store{}.

fetch(Uri, #store{documents = Documents}) ->
    maps:get(Uri, Documents, undefined).
```

`base` принадлежит самому значению реестра: иначе переданный в `new/1`
`base_uri` потерялся бы до следующего вызова `add`. Пустым реестром считается
`documents = #{}`; служебное поле с `base_uri` документом и именем реестра не
является. `new/1` без `base_uri` завершается badarg: реестр называет свои
документы, и без него имя регистрации осталось бы относительным. Значение
`anonymous` остаётся у одного `temporary/0` — реестра на один вызов компиляции,
который ничего не регистрирует и нужен лишь затем, чтобы достать встроенные
метасхемы.

У документа ровно два имени: имя регистрации и канонический URI. Если они различаются, документ доступен под обоими ключами, но лежит при этом один раз — два ключа map указывают на один и тот же терм, и внутри кучи процесса это ничего не стоит. Промежуточных записей-указателей нет, поэтому нет ни цепочек, ни циклов, ни отдельного шага разыменования при чтении.

Третьего имени не бывает. Встроенный `$id` создаёт resource, а не документ, и ссылка на него разрешается через индекс ресурсов внутри компиляции. Отдельное имя для ненормализованного написания тоже не нужно: регистрация и ссылка проходят через одну и ту же нормализацию и дают один ключ.

## Имена

Регистрация получает имя записи, разрешённое от `base_uri` хранилища, и корневой `$id`, разрешённый уже относительно него. Канонический URI берётся из `$id`, а при его отсутствии совпадает с именем регистрации. Занятое другим документом имя даёт `name_taken`, не перезапись.

Имени рядом со схемой может и не быть: retrieval URI есть у того, кто схему откуда-то достал, а вызывающий часто держит её уже в руках. Поэтому регистрация разведена на две ступени, и первая, `name_entries/2`, берёт только схемы и выводит имя из их `$id`, разрешая относительный от `base_uri` хранилища. Не назвавшая себя схема дальше не идёт: корень документа всегда является schema resource и обязан иметь абсолютное имя ([core.txt:565](../references/json-schema/draft-2020-12/core.txt)), а взять его больше неоткуда — отсюда причина `unnamed_schema` под ключом `anonymous`. Так же отвергается булев корень: `$id` в него не написать, и годится ему только имя снаружи. Вторая ступень, `add/2` реестра, как и прежде принимает одни пары, поэтому разбирать устройство аргумента не приходится ни одной из них.

| Точка входа | `$id` | `rid` / `#resource.id` |
| --- | --- | --- |
| имя регистрации | отсутствует | имя регистрации |
| имя регистрации | совпадает или отличается | разрешённый `$id`; имя регистрации остаётся вторым ключом реестра |
| схема без имени рядом | абсолютный или относительный | разрешённый `$id` |
| схема без имени рядом | отсутствует | `unnamed_schema` |
| inline term | абсолютный | `$id` |
| inline term | отсутствует | `anonymous` / `undefined` |

Отсюда правило адресации: адрес схемы — её каноническое имя. Схема, объявившая `$id`, адресуется этим `$id`; схема, не объявившая ничего, — именем, которое ей дало хранилище. Путь, по которому файл лежал, участвует в выборе канонического имени последним доводом, когда других указаний нет вовсе, и собственным адресом не становится.

Имя регистрации остаётся вторым ключом реестра, но точкой входа не служит. Нужно оно компиляции: схемы пишем не мы, и в обязательном наборе есть ссылка именно по имени регистрации на документ, объявивший другой `$id` ([refRemote.json:270](../../test/fixtures/json-schema-test-suite/tests/draft2020-12/refRemote.json)). Такую ссылку реестр разрешает и приводит к каноническому имени.

Поэтому граница проходит по моменту разрешения имени. Снаружи принимается каноническое имя, полное либо короткое; всё, что дальше — `addr()`, `#resource.id`, базовые URI, `sources` и ключ артефакта, — существует только в канонической форме. Имя регистрации остаётся ключом реестра и полем документа, нужным чтобы при удалении снять оба ключа.

В `sources` попадают канонические имена документов; embedded `$id` отдельным документом туда не добавляется. Пользовательская метасхема и её пользовательская `$schema`-цепочка входят в `sources`, хотя их nodes не входят в `resources`: они определяют dialect/profile артефакта и должны инвалидировать его при изменении. При включённой проверке туда дополнительно попадает `$ref`-замыкание пользовательской метасхемы, потому что оно участвует в meta-validation; при `{trust_schema, true}` это замыкание семантически не используется и не добавляется. Встроенные метасхемы в `sources` не входят вовсе, потому что не меняются никогда.

## Anonymous root

Inline-схема без `$id` доступна только как точка входа и не имеет абсолютной локации. Fragment-only references (`#`, `#foo`, `#/$defs/...`) разрешаются внутри anonymous resource: внешняя base URI им не нужна. Относительный path URI и относительный вложенный `$id` без базы — `relative_uri_without_base`. Абсолютный вложенный `$id` создаёт обычный именованный resource.

В реестр inline-схема не попадает, поэтому артефакта у неё нет и в таблицу она не публикуется. `compile/3` обслуживает встроенный режим, где вызывающий держит `compiled()` сам.

## Встроенные метасхемы

Метасхемы четырёх канонических диалектов лежат в [`priv/json_schema/`](../../priv/json_schema/) и образуют отдельную неизменяемую область. В `store()` их нет: `fetch` заглядывает в опубликованный bundle вторым шагом, если имя не нашлось в реестре. Пользовательские операции до этой области не дотягиваются — регистрация такого имени даёт `name_taken`, удаление его не видит, а новый реестр создаётся пустым.

Всего этих документов восемнадцать: корневая метасхема и восемь vocabulary-метасхем для Draft 2020-12, корневая и шесть для Draft 2019-09, а также по одной корневой метасхеме Draft 6 и Draft 7. Замыкание корневой 2020-12 составляют восемь документов, 2019-09 — семь, Draft 6 и Draft 7 — по одному; `format-assertion` в замыкание 2020-12 не входит и достижим только из пользовательской метасхемы, объявившей соответствующий vocabulary. Лежащие рядом `output/schema.json` в область не входят: они нужны прогонщику output tests, а не валидатору.

Скомпилированные метасхемы диалектов хранятся в `persistent_term`, по одной bundle-записи на диалект. При старте приложения все восемнадцать файлов читаются и декодируются один раз, затем доверенным bootstrap-путём без meta-validation строятся четыре корневых compiled artifact. Bundle хранит artifact вместе с map декодированных `#document{}`: поэтому и проверка resource, и обычный `$ref` на встроенный документ обходятся без повторного чтения `priv`. Отказ от `persistent_term` в разделе [про таблицу](#ets-и-процессы) их не касается: он вызван ценой обновления, а эти записи пишутся при старте и дальше не меняются. Взамен чтение не копирует терм в кучу читателя, и это заметно на проверке ресурсов метасхемой, где её достают на каждый resource.

Вторая роль метасхемы — обычная цель `$ref`, и она встречается в обязательном наборе: [ref.json:188](../../test/fixtures/json-schema-test-suite/tests/draft2020-12/ref.json) и [defs.json:6](../../test/fixtures/json-schema-test-suite/tests/draft2020-12/defs.json) в обоих диалектах ссылаются на метасхему напрямую. Такая ссылка разрешается через встроенную область как любая другая, и замыкание метасхемы попадает копией в ссылающийся артефакт.

# API и фазы компиляции

```erlang
-spec new([sopt()]) -> store().
-spec add(store(), uri(), json()) -> {ok, uri(), store()} | {error, schema_error()}.
-spec add(store(), [{uri(), json()}]) ->
    {ok, [uri()], store()} | {error, [{uri(), schema_error()}]}.
-spec remove(store(), [uri()]) ->
    {ok, [{uri(), uri()}], store()} | {error, [{uri(), schema_error()}]}.

-spec compile(store(), json(), [copt()]) ->
    {ok, compiled()} | {error, schema_error()}.
-spec compile_uri(store(), uri(), [copt()]) ->
    {ok, compiled()} | {error, schema_error()}.

%% sopt() :: {base_uri, uri()}.
%% copt() :: {default_dialect, dialect()}
%%         | {assert_format, boolean()}
%%         | {schema_validation, flag | basic | detailed | verbose}
%%         | {trust_schema, boolean()}.
```

Регистрация работает в стиле upsert: повторный `add` под тем же именем записи заменяет документ, а `name_taken` возникает, только когда имя занято другим документом. Списочные формы нужны потому, что резолв не ленивый: взаимно ссылающиеся документы обязаны появиться в реестре одним вызовом, иначе первый из них упадёт на неразрешённой ссылке. `remove/2` снимает оба ключа документа — ради этого имя регистрации и хранится полем. Снятые документы он называет парами «написание вызывающего — каноническое имя»: первым называется ошибка, вторым лежит артефакт, и это разные строки. Запись, не нашедшая документа, пары не даёт и ошибкой не считается: удалять нечего, а встроенное имя реестру и вовсе не видно. Ошибки разрешения имён `remove/2` собирает все, как и списочный `add`.

Списочный `add` собирает все ошибки, а не первую: записи разбираются независимо, и показать разом весь испорченный вызов полезнее, чем одну запись за прогон. Названа каждая ошибка тем написанием, с каким пришёл вызывающий, — канонического имени у отвергнутой записи может не быть вовсе, а `name_taken` называет чужое. Фазы при этом не смешиваются: пока хоть одно имя не разрешилось, конфликты не считаются, потому что документов ещё нет. Внутри фазы конфликтов отвергнутая запись не вставляется, а обход продолжается, и невидимым остаётся ровно один конфликт — с записью, которая и сама отвергнута. Атомарность от сбора ошибок не страдает: при любой ошибке не регистрируется ничего. Одиночный `add/3` возвращает ошибку без имени, потому что запись там одна и вызывающий её знает.

`add` делает только корневой проход и не компилирует, а возвращает канонические имена: под ними документ известен дальше, и под ними же его артефакт лежит в таблице. `compile_uri/3` сохраняет имя точки входа и base URI; `compile/3` работает с термом вне реестра. Inline `$id`, занятый другим документом, отвергается.

Имена, попадающие в реестр, разрешаются относительно `base_uri`, заданного при создании. Поэтому короткая форма вроде `product/banana` допустима наравне с полной: один и тот же путь обрабатывает оба вида, а абсолютное имя разрешение оставляет неизменным. `base_uri` обязан быть иерархическим — относительно URN разрешение молча теряет часть имени, превращая `product/banana` при `urn:example:root` в `urn:product/banana`. Завершающий слэш дописывается нормализацией: без него разрешение съело бы последний сегмент, и `product/banana` под `https://shop.service/schemas` попало бы в `https://shop.service/product/banana`. Query у `base_uri` запрещён: разрешение его всё равно отбрасывает, а дописывать слэш было бы некуда. Сама сокращённая форма нигде не хранится, второго ключа в реестре от неё не появляется. Правило разрешения публикуется как `resolve_name/2` и служит не одной регистрации: чтение артефакта зовёт его же, поэтому короткое имя, принятое `add`, находится и у `validate`.

Компиляция идёт от точки входа и втягивает все документы, достигнутые через `$ref`, а также profile dependencies пользовательских метасхем, названных в `$schema`. Канонический dialect URI документа не втягивает: соответствующая метасхема берётся из встроенной области. Порядок регистрации не важен, но реестр должен быть полон. Фазы фиксированы:

1. выбрать dialect корней документов и нарезать resources по `$id`;
2. построить все schema nodes, индексы anchors и временный индекс физических
   locations;
3. разрешить URI/fragments в канонические `addr()`;
4. если `trust_schema = false`, проверить каждый resource его метасхемой,
   когда нужные referencing keywords уже реализованы;
5. испустить замкнутый `compiled()` либо вернуть первую `schema_error()`.

Резолв не ленивый: dangling refs и отсутствующие documents обнаруживаются до валидации. Нормативные тексты лежат локально: [RFC 3986](../references/rfc/rfc3986.txt) и [RFC 6901](../references/rfc/rfc6901.txt), карта нужных секций — в [rfc overview](../references/rfc/overview.md).

## Location aliases для embedded resources

Подсхема внутри embedded resource имеет канонический адрес относительно его
собственного `$id`, но физически остаётся доступна JSON Pointer'ом относительно
каждого объемлющего resource. Например, корень resource `bar` в позиции
`/items` документа `foo` обозначается и URI `foo#/items`, хотя его канонический
адрес — `{bar, <<>>}`. Этот parent-pointer URI поддерживается: исключать его из
профиля нельзя без исключения обязательных групп Draft 2019-09.

Compiler строит на второй фазе эфемерный индекс:

```erlang
-type location_index() :: #{{rid(), pointer()} => addr()}.
```

Для каждого schema node индекс содержит его канонический адрес и физический
pointer относительно каждого объемлющего resource. Если retrieval URI документа
отличается от его канонического URI, весь pointer space от корня документа
дополнительно индексируется под retrieval URI. Поэтому вложенный embedded
resource индексируется не только под непосредственным родителем, но и под всеми
предками. У анонимного корня роль базы внутри fragment-only references выполняет
`anonymous`.

На третьей фазе любая ссылка сначала ищется в этом индексе и сразу превращается
в единственный канонический `addr()`. После компиляции индекс отбрасывается: он
не входит ни в `store()`, ни в `compiled()`, ни в `#resource.nodes`. Location
alias не является третьим именем документа и не участвует в регистрации,
удалении или invalidation. Благодаря этому cycle guard, dynamic scope и
`absoluteKeywordLocation` видят только канонический адрес.

## Слой URI

Уровень L1 целиком опирается на модуль `uri_string` из stdlib. Он реализует разбор по RFC 3986, разрешение относительной ссылки в strict-режиме и нормализацию, поэтому собственный парсер не нужен и список зависимостей проекта остаётся пустым.

Резолв одной ссылки выглядит так:

```erlang
resolve(RefBin, BaseUri) ->
    case uri_string:parse(RefBin) of
        {error, _, _} -> {error, invalid_uri};
        Ref           -> resolve_parts(Ref, BaseUri)
    end.

resolve_parts(Ref, BaseUri) ->
    Frag   = maps:get(fragment, Ref, undefined),
    NoFrag = uri_string:recompose(maps:remove(fragment, Ref)),
    case uri_string:resolve(NoFrag, BaseUri) of
        {error, invalid_scheme, _} -> {error, relative_uri_without_base};
        {error, _, _}              -> {error, invalid_uri};
        Abs ->
            case classify(Frag) of
                {error, _} = E -> E;
                Target         -> {ok, uri_string:normalize(Abs), Target}
            end
    end.

classify(undefined)    -> root;
classify(<<>>)         -> root;
classify(F) ->
    case uri_string:percent_decode(F) of
        {error, _, _}         -> {error, invalid_percent_encoding};
        <<>>                  -> root;
        <<"/", _/binary>> = P -> {pointer, tokens(P)};
        Name                  -> {anchor, Name}
    end.
```

Порядок шагов обязателен. Fragment отделяется до разрешения, потому что в registry lookup он не участвует. Нормализация выполняется после resolve, а не до: на относительной ссылке `uri_string:normalize` молча возвращает вход неизменным, поэтому ранняя нормализация не выявила бы отсутствие базы, а замаскировала бы его.

Fragment-only ссылка проходит тем же путём без отдельной ветки. У неё пустой path, `recompose` даёт пустую строку, а разрешение пустой ссылки возвращает сам base URI — это same-document reference ([rfc3986.txt:1482](../references/rfc/rfc3986.txt)).

### Каноническая форма имени

Ключом реестра служит результат `uri_string:normalize`, то есть scheme-based normalization ([rfc3986.txt:2259](../references/rfc/rfc3986.txt)). Она приводит схему и хост к нижнему регистру, убирает порт по умолчанию и dot-сегменты, раскрывает percent-encoding unreserved-символов и не трогает регистр пути.

Выбор проверен на корпусе: из 171 абсолютного URI в fixtures и remotes нормализация не меняет ни одного, поэтому на conformance она не влияет ни в одну сторону. Смысл её в пользовательских схемах, где документ зарегистрирован под одним написанием, а ссылка приходит под другим. Риск противоположного рода приемлем: если нормализация сведёт два имени, которые автор считал разными, компиляция остановится на `name_taken`, то есть громкой ошибкой, а не подменой цели.

Пустой fragment отрезается до нормализации. Эквивалентность URI с пустым фрагментом и без него не входит в RFC-нормализацию, и спецификация прямо предупреждает, что полагаться на её поддержку в generic-библиотеках нельзя ([core.txt:1535](../references/json-schema/draft-2020-12/core.txt)).

Отдельного ключа под исходное написание не заводится: регистрация и ссылка проходят через одну и ту же нормализацию, поэтому оба написания дают один ключ и для резолва второе имя не нужно. Написание, с которым пришёл вызывающий, стоит удержать только ради текста ошибки: `name_taken` невозможно объяснить пользователю, который видит в схеме ровно то имя, которое написал.

### Fragment

Fragment декодируется целиком и ровно один раз, и лишь затем читается как JSON Pointer. Это буквальное следствие URI fragment identifier form ([rfc6901.txt:261](../references/rfc/rfc6901.txt)): указатель кодируется в октеты и percent-encoding накладывается поверх, значит обратный порядок операций — сначала снять percent-encoding, потом разбирать. Отсюда следует, что `#/$defs/a%2Fb` даёт три сегмента, а не один сегмент `a/b`. Официальные fixtures такой случай не покрывают, поэтому правило объявлено здесь. Однократность важна отдельно: `%2525` за два прохода дал бы `%` вместо правильного `%25`.

Разбиение на сегменты идёт по `/`, ведущий пустой элемент отбрасывается, затем в каждом сегменте раскрывается сначала `~1`, потом `~0` ([rfc6901.txt:95](../references/rfc/rfc6901.txt)). Обратный порядок превратил бы `~01` в `/`. Пустые сегменты сохраняются: в `ref.json` есть цель `#/$defs//$defs/`, где пустая строка является настоящим именем ключа.

Fragment без ведущего `/` считается plain-name anchor и ищется в индексе; промах даёт `unresolved_anchor`. В Draft 6/7 такое имя объявляет fragment-only `$id`, в Draft 2019-09/2020-12 — `$anchor`. Синтаксической проверки на стороне ссылки нет, потому что грамматика anchor зависит от диалекта цели, который в момент разбора ссылки ещё не выбран: Draft 2020-12 требует `^[A-Za-z_][-A-Za-z0-9._]*$`, а Draft 6/7 и Draft 2019-09 допускают ещё и двоеточие. Грамматики закреплены метасхемами, поэтому строгость достаётся в точке объявления.

### Не-иерархические схемы

URN и прочие схемы без authority обрабатываются общими правилами RFC 3986, без знания их внутренней структуры. Относительная ссылка внутри URN-ресурса при этом разрешается формально корректно, но бессмысленно: `sibling.json` относительно `urn:uuid:...` даёт `urn:sibling.json`. Специального запрета нет, потому что такое имя просто не найдётся в реестре и ссылка упадёт как незарегистрированная. В корпусе внутри URN-ресурсов встречаются только абсолютные и fragment-only ссылки.

## Уже зафиксированные правила resolution

Слой URI не отменяет остальных границ контракта:

- URI до fragment разрешается относительно текущего base URI по алгоритму RFC 3986 ([rfc3986.txt:1661](../references/rfc/rfc3986.txt)); fragment не участвует в registry lookup.
- Empty fragment и `#` обозначают корень выбранного resource. Это same-document reference ([rfc3986.txt:1482](../references/rfc/rfc3986.txt)).
- JSON Pointer fragment ищется только среди заранее построенных schema nodes ([rfc6901.txt:95](../references/rfc/rfc6901.txt)); существующий JSON value в non-schema position не является допустимой целью.
- Plain-name fragment разрешается через static anchor index; dynamic/recursive selection начинается лишь после существования лексической цели.
- URI resource хранится без fragment. Результат успешного resolution всегда канонизируется в `addr()` и не переигрывается evaluator'ом.
- Конфликты имён документов обнаруживаются до построения IR; молчаливая смена target запрещена.

Compiler держит множество уже загруженных documents и resources, поэтому взаимные междокументные refs не вызывают бесконечной компиляции. При этом каждый target проверяется после полного построения pointer space: ранний ref может указывать на node, встреченный позже в тексте.

`sources` — множество документов реестра, от которых зависит именно эта компиляция: entry document, transitive ref documents и пользовательские метасхемы, определяющие profile. При обычной проверке сюда входит также `$ref`-замыкание пользовательской метасхемы; trusted-компиляция его не исполняет и потому не включает. Встроенные метасхемы в `sources` не входят. Порядок списка не имеет семантики; для детерминированных golden terms compiler должен выбрать устойчивую сортировку.

# Dialect и vocabularies

Dialect resource выбирается так:

1. корневой `$schema` resource;
2. dialect объемлющего resource;
3. `default_dialect` компиляции, по умолчанию Draft 2020-12.

Для четырёх канонических dialect URI набор keywords встроен, а сами метасхемы берутся из [встроенной области](#встроенные-метасхемы). Пользовательская метасхема Draft 2019-09/2020-12 загружается из `store()`, а её `$vocabulary` задаёт активные keywords. Неизвестный vocabulary со значением `true` — ошибка, с `false` — игнорируется; Core обязателен и должен быть `true`. Метасхема без `$vocabulary` считается объявившей все vocabularies своего draft: Core этого требует прямо ([core.txt:1306](../references/json-schema/draft-2020-12/core.txt)), а остальные разделы велят считать свой vocabulary объявленным со значением `true`. В Draft 6/7 `$vocabulary` отсутствует, поэтому custom meta-schema наследует полный фиксированный набор keywords своего draft. Draft самой метасхемы выбирается тем же правилом, что и dialect обычного документа, поэтому цепочка метасхем разрешается рекурсивно и под guard: метасхема, зацикленная на себе, dialect не определяет. Сам `$vocabulary` действует только при обработке документа как метасхемы.

Поддерживаемые URI vocabularies:

- Draft 2020-12: `core`, `applicator`, `unevaluated`, `validation`, `meta-data`, `format-annotation`, `content`;
- Draft 2019-09: `core`, `applicator`, `validation`, `meta-data`, `format`, `content`.

Итого это 13 URI, потому что префикс dialect входит в имя. В корневой метасхеме 2019-09 `format` объявлен `false`, остальные перечисленные vocabularies — `true`.

Dispatcher компилятора — функция `(active vocabularies, keyword)`. Keyword активного vocabulary создаёт constraint; прочий keyword становится неизвестным — annotation в 2020-12, no-op в Draft 6/7/2019-09. Различия впечатаны в IR; evaluator dialect не читает.

Стандартные метасхемы добавляют compatibility-имена сверх формальных
vocabularies. `definitions` — native schema container Draft 6/7 и
location-reserving alias `$defs` в Draft 2019-09/2020-12. `dependencies`
активен только в Draft 6/7 и объединяет property и schema forms; в новых
dialects он остаётся unknown keyword. `$recursiveRef` и `$recursiveAnchor`
активны только в Core vocabulary Draft 2019-09; одноимённые deprecated
properties корневой метасхемы 2020-12 лишь резервируют форму и не дают им
recursive-семантики.

`assert_format` меняет IR и потому является compile option. По умолчанию `format` аннотирует. Format-Assertion vocabulary требует проверки независимо от опции; неизвестное имя при ней — compile error ([validation.txt:714](../references/json-schema/draft-2020-12/validation.txt)), а при опции остаётся annotation-only. Состав таблицы format algorithms выбран и записан в [«Format attributes»](format-attributes.md), но четыре имени — `idn-email`, `idn-hostname`, `iri`, `iri-reference` — являются документированным исключением и остаются чистой аннотацией. Поскольку их проверки намеренно нет, Format-Assertion не поддержан: метасхема, объявившая его значением `true`, отвергается — спецификация требует именно отказа от реализации без полной проверки. Значение `false` игнорируется, как у любого неподдержанного vocabulary.

Аннотация `format` от объявления vocabulary не зависит. В Draft 2019-09 это требование спецификации: собирать аннотацию нужно независимо от boolean, а в корневой метасхеме он как раз `false` ([validation.txt:601](../references/json-schema/draft-2019-09/validation.txt)). В Draft 2020-12 keyword определяется своей vocabulary, но выключенный `format` попадает в unknown keywords и становится annotation с тем же именем и значением, поэтому наблюдаемый unit тот же.

# Проверка схем и ошибки

По умолчанию каждый schema resource проверяется отдельно своей метасхемой; compound document целиком как один instance не проверяется ([core.txt:2139](../references/json-schema/draft-2020-12/core.txt)). При построении instance объемлющего resource позиции embedded resources заменяются на `true`: сам контейнер остаётся проверяемым, а содержимое вложенного resource не получает ошибочно dialect родителя и следующим шагом проверяется отдельно. Провал возвращает `schema_invalid`; формат вложенного validation output задаёт compile option `schema_validation`, по умолчанию `basic`.

`{trust_schema, true}` отключает весь meta-schema evaluation pass. Этой опцией вызывающий утверждает, что schema resources уже проверены вне текущей компиляции. Поведение malformed schema в таком режиме implementation-defined: compiler по-прежнему может отвергнуть значение защитной проверкой, но meta-schema error больше не обещан. Значение по умолчанию — `false`.

Trust не отключает выбор dialect/profile, обработку `$schema` и `$vocabulary`, проверку обязательных vocabularies, resource discovery, URI/reference resolution, компиляцию regex, защитные проверки emitter и последующую validation instance. Поэтому пользовательская метасхема и вся её пользовательская `$schema`-цепочка остаются в `sources`. Её `$ref`-замыкание добавляется только при включённом meta-validation: trusted artifact ограничения метасхемы не исполняет и от этого замыкания не зависит.

Метасхемы встроенной области компилируются доверенно один раз при старте и кладутся в `persistent_term`, иначе возникает bootstrapping cycle. При включённой проверке пользовательская метасхема остаётся обычным документом `store()`, компилируется с локальным cache один раз на текущую компиляцию, а её собственный и транзитивные documents входят в `sources`, но не в `resources` проверяемого artifact только из-за `$schema`. Механизм включается в P6 сразу для обоих dialects: корневой метасхеме 2020-12 кроме `$dynamicRef` нужны `$vocabulary` и `format`, а метасхеме 2019-09 — ещё и recursive keywords этой фазы.

Разделение обязанностей:

| Проверка | Кто выполняет |
| --- | --- |
| типы, границы и формы standard keywords | meta-schema соответствующего resource, если `trust_schema = false`; иначе гарантия вызывающего |
| выбор `$schema` и обязательных vocabularies | compiler до запуска meta-schema |
| regex dialect/compileability | compiler/format policy |
| URI, registry presence и schema target | compiler resolution phase |
| `$schema`/`$vocabulary` вне допустимой позиции | compiler |
| невозможное значение для IR slot | страховочный compiler check |

В checked-режиме meta-schema остаётся единственным источником синтаксической правды. В trusted-режиме эту гарантию предоставляет вызывающий, а compiler сохраняет собственные проверки, необходимые для тотальности, URI/reference semantics и построения IR.

```erlang
-record(schema_error, {
    reason   :: reason(),
    location :: addr() | undefined
}).

-type reason() ::
      invalid_uri | invalid_percent_encoding | relative_uri_without_base
    | {dangling_ref, addr()} | {non_schema_target, addr()}
    | {unknown_document, uri()}
    | {bad_pattern, term()} | {bad_keyword_value, json()}
    | {unknown_dialect, uri()} | {unrecognized_vocabulary, uri()}
    | core_vocabulary_missing | {misplaced_keyword, binary()}
    | {schema_invalid, #output_unit{}}
    | {metaschema_evaluation_failed, uri(), eval_error()}
    | {name_taken, uri()} | {referenced_by, uri(), [uri()]}.

-spec format_error(#schema_error{}) -> unicode:chardata().
```

Первая ошибка прерывает компиляцию. `location` указывает на keyword, у регистрации она `undefined`. Текст вычисляет `format_error/1`, он не дублируется в записи. В checked-режиме проверка метасхемой покрывает синтаксис; compiler оставляет ошибки, возникающие до её выбора, при URI/reference resolution, при `format`, а также защитный `bad_keyword_value`. В trusted-режиме `schema_invalid` не возникает, но остальные compile errors сохраняются.

Одна ошибка, а не список, следует из фаз: повреждение resource slicing делает поздние node/ref errors недостоверными. Накопление потребовало бы отдельного IR для повреждённых nodes. Структура `schema_error()` тестируется точно; `format_error/1` — отдельно и слабо, чтобы редактирование текста не меняло машинный контракт.

`{referenced_by, Uri, Refs}` стоит особняком: он возникает не при компиляции, а при попытке удалить документ, на который ссылаются перечисленные. Ошибка называет ссылающихся, чтобы вызывающий узнал конус зависимых из неё самой, а не вычислял его вслепую.

Провал instance validation к этому каталогу не относится: `{ok, Output}` с `valid = false` — штатный результат core. Ошибка `validate/3` резервируется за схемами, у которых вердикта нет: за циклом in-place applicators, пойманным cycle guard'ом.

# Runtime ownership

Библиотека используется в двух режимах. Во встроенном вызывающий сам зовёт `compile/3`, держит `compiled()` в состоянии своего процесса и передаёт в `valid_json_core:validate/3`; ни таблицы, ни процессов при этом не нужно, и conformance-прогон работает именно так. Тому, кто держать артефакт не собирается, фасад даёт `run_schema/3`: обе половины одним вызовом и без хранения. Размещённый режим добавляет поверх общее хранение артефактов, и всё дальнейшее относится только к нему.

Слой разделён на три уровня:

| Уровень | Знает | Не знает |
| --- | --- | --- |
| core/resources | чистые `store()` и `compiled()` | ETS и процессы |
| таблица | имя, layout, владение и чтение | что и когда писать |
| управляющий | документы, options, reload | устройство IR |

Хранилищ бывает несколько: приложения держат собственные наборы схем и делить
их между собой не обязаны. Хранилище задаётся именем-атомом, которое передаёт
приложение. Таблиц у хранилища две: артефакты лежат в таблице, названной именем
самого хранилища, документы реестра — в `Name_registry`. Процессы называются по
тому, чем заведуют: `Name_manager` у управляющего и `Name_keeper` с
`Name_registry_keeper` у хранителей, то есть имя хранителя выводится из имени
его таблицы и разными оказывается само собой. Имя приходит из кода или
конфигурации разработчика и никогда из пользовательского ввода: атомы,
выведённые из внешних данных, засоряют таблицу атомов. Столкновение имён
обнаруживается громко — `ets:new` второго хранилища завершится `badarg`, и оно
просто не поднимется, вместо того чтобы молча разделить чужую таблицу.

Уровень таблицы состоит из двух модулей. Хранитель — процесс, поэтому таблица
живёт ровно столько, сколько живёт он:

```erlang
-spec start_link(atom(), [term()]) -> {ok, pid()}.
-spec keeper_name(atom()) -> atom().
-spec claim(atom()) -> ok | {error, not_owner}.
```

Спеки потомка хранитель о себе не даёт: перезапуск, остановка и `id` — политика
того, кто его ставит, а ставит его только супервизор хранилища, и там же принято
решение о порядке. Описывать себя для чужого дерева хранителю незачем: за его
пределы он не выходит.

Таблица у хранителя ровно одна, и это не экономия, а следствие механики:
`give_away` и `heir` действуют на одну таблицу, поэтому хранитель на две имел бы
половинчатое состояние в отказной ветке `claim` — первую отдали, на второй
отказ. Хранилищу, которому нужны две таблицы, ставят двух хранителей.

Из опций таблицы хранитель ставит сам только две: `named_table`, на котором
держится всё именование, и `heir`, равный самому хранителю, — ради него
хранитель и заведён. Остальные приходят параметром от управляющего, потому что
тип, защита и режимы доступа принадлежат тому, кто знает содержимое таблицы.
Хранитель о содержимом не знает ничего: подарком при передаче служит имя
таблицы, а слова «хранилище» в модуле нет вовсе.

`claim/1` вызывает управляющий, и хранитель отвечает на него `ets:give_away/3`.
Владение переходит в самом `give_away`, а `'ETS-TRANSFER'` является только
уведомлением, поэтому вызывающему достаточно дождаться ответа, а хранителю — не
делать по этому сообщению ничего. После передачи таблицы управляющему хранитель
остаётся её heir.

`claim/1` тотален, потому что иначе единственная точка входа хранителя умела бы
его убить: `ets:give_away/3` разрешён только владельцу, и повторный вызов
завершался бы `badarg`, унося таблицу вместе с процессом. Поэтому повторный
`claim` от нынешнего владельца отвечает `ok` и таблицу не трогает, а `claim` при
живом постороннем владельце — `{error, not_owner}`, оставляя решение
вызывающему. Это единственная развилка в модуле, и она существует ради того,
чтобы у хранителя не осталось пути к падению.

Клиент читает таблицу в процессе вызывающего и о процессах не знает вовсе:

```erlang
-spec lookup(atom(), uri()) ->
    {ok, compiled()} | {error, not_found} | {error, unavailable}.
```

Он же остаётся единственным местом, знающим, как имя хранилища превращается в
имена таблиц. Если когда-нибудь понадобится диспетчер с подменой таблиц, правка
придётся сюда, а вызывающие останутся прежними.

Имя документа он принимает и коротким. Сперва имя пробуется как есть, и
канонический вызов этим и заканчивается — одним чтением. Только промах читает
`base_uri` из таблицы реестра, разрешает от него имя и повторяет чтение, поэтому
второе чтение достаётся коротким именам и неизвестным. Правило разрешения при
этом одно на всё хранилище: и регистрация, и чтение зовут `resolve_name/2`
реестра, иначе имя, принятое `add`, могло бы не найтись у `validate`.
Fragment остаётся промахом: в registry lookup он не участвует.

`base_uri` читается из таблицы, потому что состояние управляющего читателю не
видно, а будить его на горячем пути незачем. Строка эта односторонняя: истина —
`#store.base` управляющего, в таблицу она пишется один раз при старте и обратно
не читается никогда.

Промах отвечает `not_found`, только когда в таблице артефактов стоит `ready`;
без неё, а равно без самой таблицы, ответ — `unavailable`. Смысл разделения и
все случаи, когда отметки нет, описаны [в разделе про
готовность](#готовность). Отметка читается раньше разрешения короткого имени:
пока набор неполон, разрешать нечего. Зато после неё пропавшая строка с
`base_uri` промах уже не меняет — о готовности хранилище сказало, а разрешить
короткое имя не от чего.

Отсюда требование к самому чтению: отсутствующей таблицы оно не боится и падать
на ней не вправе — таблицы пересоздаются при перезапуске хранителей, и попасть в
это окно читатель может в любой момент.

Запись в этот уровень не входит: писать может только владелец, то есть
управляющий, и пакетная транзакция принадлежит ему вместе с решением, что в неё
попадёт. Функции перечисления имён нет — множество имён управляющий знает из
собственного `store()`.

## Хранилище в дереве приложения

Три процесса живут под собственным супервизором со стратегией `rest_for_one`:
хранитель реестра, хранитель артефактов, управляющий. Библиотека даёт два
способа поднять хранилище.

```erlang
-spec child_spec(atom(), [store_option()]) -> supervisor:child_spec().
-spec start_link(atom(), [store_option()]) -> {ok, pid()}.

%% store_option() :: {base_uri, uri()}
%%                 | {default_dialect, dialect()}
%%                 | {assert_format, boolean()}
%%                 | {trust_schema, boolean()}
%%                 | {loader, {module(), term()}}.
```

Здесь спека потомка у самого модуля и остаётся: это точка встраивания в чужое
дерево, и супервизор хранилища описывает себя тому, кто его ставит. Фасад
повторяет её как `store_child_spec/2`, чтобы за спекой не приходилось идти в
исходники.

Приложение, которому нужно собственное хранилище, встраивает `child_spec/2` в
своё дерево: время жизни хранилища совпадает с временем жизни владельца, порядок
старта виден в его дереве, а библиотека не заводит никакого глобального
состояния сверх стандартного хранилища. Приложению, которому достаточно общего,
ничего встраивать не нужно: дерево библиотеки всегда поднимает хранилище с
именем `valid_json`, и его процессы называются `valid_json_keeper`,
`valid_json_registry_keeper` и `valid_json_manager`. Поэтому корень библиотеки —
`one_for_one` над стандартным хранилищем, а `rest_for_one` относится к одному
хранилищу, а не ко всей библиотеке.

`base_uri`, `default_dialect`, `assert_format`, `trust_schema` и `loader` —
опции хранилища целиком, а не отдельной записи: все пять применяются ко всему
хранилищу сразу.

`base_uri` обязателен и передаётся только опцией. Им хранилище заявляет о
принадлежности своих схем сервису, поэтому два хранилища над одним каталогом
под `https://shop.service/schemas/` и `https://internal.service/schemas/` дают
разные имена одним и тем же документам. Такое решение принимает разработчик, и
подставить за него умолчание нельзя: хранилище без `base_uri` завершается
badarg. Стандартному хранилищу его называет сама библиотека —
`https://valid_json.internal/schemas/`; домен `.internal` зарезервирован ICANN
за частными сетями, поэтому имя схемы не совпадёт с адресом, за которым
что-нибудь отвечает.

Остальные четыре разрешаются по одному правилу: опция, переданная при создании;
затем app env библиотеки; затем встроенное умолчание. Для стандартного
хранилища app env — единственный способ их задать: поднимает его дерево
библиотеки, и опций ему передать неоткуда. Именно так приложение и просит
загрузить каталог, не заводя собственного хранилища и не вызывая ничего при
старте.

`trust_schema` по умолчанию равен `false` и задаёт trust boundary всего
хранилища. Значение `true` одинаково действует на loader startup, последующие
`add`/`add_at`, rebuild зависимых артефактов и восстановление после потери
artifact table. Хранилище не различает происхождение отдельных записей: если
trusted loader и внешние добавления имеют разную степень доверия, им нужны
разные stores.

Работать с названным хранилищем приложение может и напрямую, но обычно заводит
собственную обёртку в одну строку, подставляющую своё имя. Библиотека этого не
навязывает и своей стороной вопроса не занимается.

## Загрузчик схем

Схемы приложения обычно лежат там же, где лежит оно само: в каталоге рядом с
релизом, за HTTP или в базе. Хранилище берёт их оттуда само, если ему задан
загрузчик; вызовы `add` и `remove` остаются для схем, которые приходят к
приложению уже в работе.

```erlang
-callback load(Args :: term()) -> {ok, [{uri(), json()}]} | {error, term()}.
```

Загрузчик задаётся опцией `{loader, {Module, Args}}` и потому бывает у
хранилища ровно один: второй опции взяться неоткуда. Собрать набор из двух мест
приложение может загрузчиком-композитом, и это его дело, а не второе поле в
контракте.

Колбэк один, и граница здесь та же, что между физическим хранением и
адресацией: где схемы лежат, знает загрузчик, а как они называются, решает
хранилище. Имени схемы загрузчик не назначает и `base_uri` не предлагает —
иначе путь к файлу протёк бы в адрес схемы.

`load/1` делает ввод-вывод и вызывается в `handle_continue`, то есть уже после
возврата из `init`. Поэтому дерево поднимается быстро и старт приложения не
держит, а вызовы к управляющему дожидаются конца загрузки сами собой:
`handle_continue` выполняется раньше любого сообщения. Реестр к этому моменту
уже собран: `base_uri` пришёл опцией и ждать загрузчика ему незачем.

Набор возвращается целиком и уходит в один `add`. Отсюда правило «реестр всегда
целиком компилируем» выполняется даром: взаимно ссылающиеся файлы каталога
попадают в реестр одним вызовом, и оговорка про один вызов остаётся только тем,
кто добавляет схемы руками.

Имена в наборе относительные, а абсолютными их делает `base_uri` хранилища. Так
один и тот же каталог годится любому хранилищу: файл `product/banana.json`
окажется под именем `https://shop.service/schemas/product/banana.json` в одном
и под `https://internal.service/schemas/product/banana.json` в другом, а
относительные ссылки внутри схем сойдутся в обоих случаях. Схема, объявившая
`$id`, в обоих случаях адресуется своим `$id`, и от того, куда её положили, её
адрес не зависит вовсе.

Библиотека поставляет загрузчик каталога. Загрузчика базы данных в ней нет и
быть не может: ни драйвера, ни раскладки таблиц библиотека не знает, и ровно для
этого случая заведено поведение — приложение пишет собственный модуль. Загрузчик
HTTP проектируется отдельно: перечислить схемы по URL нельзя, листинга у HTTP
нет, поэтому ему понадобится либо явный список имён, либо индексный документ.

### Каталог

`valid_json_loader_dir` обходит каталог рекурсивно, берёт файлы по расширению
(`.json` по умолчанию) и называет документ путём файла относительно корня. Имя
это относительное и адресом само по себе не становится: абсолютным его делает
`base_uri` хранилища, а схема, объявившая `$id`, называется своим `$id`.

Называют корень две взаимоисключающие опции. `{root, Path}` берёт путь как есть,
поэтому относительный путь считается от рабочего каталога узла. `{priv_dir, App,
Path}` ищет путь внутри приватного каталога приложения: в релизе рабочий каталог
заранее не известен, а `priv` известен всегда. Путь внутри `priv` проверяется до
всякого чтения и наружу не уводит — ни абсолютным видом, ни `..`, ни символьной
ссылкой. Обе опции сразу — такая же ошибка конфигурации, как и приложение,
которого нет в коде: требовать ровно одну проще, чем объяснять, какая из двух
победила.

За пределы корня обход не выходит. Тип записи он берёт `file:read_link_info/1`,
которая по символьной ссылке не идёт, поэтому обходятся только настоящие
каталоги и читаются только настоящие файлы. Уйти из области при таком устройстве
нечем, и ссылка на собственный предок обход не зацикливает. Молча ссылка не
пропускается: с именем вроде `weight.json` она от схемы неотличима, и потерянный
документ обошёлся бы дороже отказа, называющего путь. Ссылка, никуда из области
не уходящая, отвергается наравне с прочими — проверять её цель дороже, чем
положить схему в саму область.

Сегменты пути становятся сегментами URI посимвольным экранированием: unreserved
и sub-delims остаются как есть, остальное превращается в percent-encoding, а в
первом сегменте экранируется ещё и двоеточие, иначе относительная ссылка
прочиталась бы как scheme. Обычное имя вроде `product/banana.json` при этом не
меняется ни на байт, поэтому написанный в схеме относительный `$ref` попадает
ровно в ту же цель.

Расширение остаётся частью имени. Отбросить его значило бы придумать имя,
которого на диске нет, а каноническое имя документ и так назначает себе сам,
если несёт `$id`.

Нечитаемый файл и неразбираемый JSON — отказ загрузчика, называющий путь.

### Когда загрузчик читается

Один раз: на холодном старте хранилища и после потери реестра. Перезапуск
управляющего его не зовёт — набор документов пережил управляющего в таблице
реестра, а повторное чтение вернуло бы снятое через `remove` и стоило бы
сетевому загрузчику полной загрузки при каждом рестарте.

Признаком служит не пустота реестра — приложение вправе снять все документы, —
а служебная строка. Строк таких две, и каждая лежит в той таблице, о которой
говорит:

| Строка | Таблица | Значит | Пишется |
| --- | --- | --- | --- |
| `loaded` | реестра | загрузчик уже прочитан | следом за его документами |
| `ready` | артефактов | артефакты полны относительно реестра | после сборки, в `handle_continue` |

Отметка `loaded` идёт следом за документами, а не тем же коммитом, и разрыв
между ними безвреден: смерть управляющего в этом промежутке приведёт к
повторному чтению загрузчика, а оно заменит те же документы теми же.

Снимать отметки не нужно ни в одном случае: каждая исчезает вместе со своей таблицей,
а таблица исчезает ровно в том отказе, который её содержимое обесценивает.
Поэтому все четыре случая разбираются устройством, а не отдельной проверкой:

- **холодный старт** — нет ни одной строки: загрузчик читается, `ready`
  появляется после сборки;
- **умер управляющий** — целы обе, чтение не прерывается ни на мгновение,
  загрузчик молчит;
- **умер хранитель артефактов** — `loaded` цела, `ready` исчезла вместе с
  таблицей: артефакты пересобираются из реестра, загрузчик молчит;
- **умер хранитель реестра** — исчезли обе, и загрузчик читается заново.

Последний случай и есть та полная пересборка, которую [разбор
отказов](#ets-и-процессы) оставлял приложению: с загрузчиком хранилище
восстанавливает набор само.

Одна отметка вместо двух была бы неверной. Строка в таблице реестра переживает
смерть хранителя артефактов и говорила бы «готово» о наборе, которого уже нет.
Ставить её заново при каждом старте управляющего тоже нельзя: смерть одного
управляющего окна чтения не открывает вовсе, и хранилище объявляло бы себя
неготовым там, где всё исправно работает.

Отказ загрузчика валит управляющего той же логикой, по какой его валит отказ
компиляции в `handle_continue`: отсутствующий каталог или испорченный файл —
расхождение конфигурации, и поднимать хранилище с дырой в наборе не за чем.
Повторные попытки при сетевом загрузчике принадлежат самому загрузчику, внутри
его `load/1`.

### Готовность

`handle_continue` выполняется раньше любого сообщения, поэтому изменяющие вызовы
ждут конца загрузки сами. Чтение таким свойством не обладает: `lookup` читает
таблицу в процессе вызывающего и управляющего не спрашивает. Отсюда две вещи в
контракте.

```erlang
-spec wait(atom(), timeout()) -> {ok, reference()} | {error, timeout}.
```

`wait` возвращает не `ok`, а монитор, и ставит его сам, до подтверждения
готовности. Иначе между «готово» и `erlang:monitor` вызывающего помещалась бы
смерть управляющего, о которой он уже не узнал бы. Обратный порядок безвреден:
если управляющий умер и переродился между монитором и вызовом, придёт `DOWN` о
прежнем, вызывающий сочтёт хранилище неготовым и позовёт `wait` ещё раз. Имя в
промежутке перезапуска бывает не зарегистрировано, и `wait` повторяет попытку
сам до истечения `Timeout`: вызывающий написал бы тот же цикл.

Толковать `DOWN` как «читать нельзя» не следует. Смерть одного управляющего окно
чтения не открывает: обе таблицы уходят к хранителям по `heir` вместе с
содержимым, `ready` остаётся на месте, и `lookup` работает всё время его
перезапуска. Окно открывает только смерть хранителя — и тогда `DOWN` приходит
тоже, потому что `rest_for_one` уносит управляющего следом. То есть монитор
ловит оба события одним механизмом, но означает он «состав мог измениться,
переспроси», а не «данных нет».

Второе — ответ `{error, unavailable}` у чтения. Он покрывает все случаи, когда
хранилище ответить не может: не поднято, перезапускается, читает загрузчик,
пересобирает артефакты. Разделять их незачем — сделать с ними вызывающему можно
одно и то же, подождать; а отличать их от `not_found` необходимо, потому что
для вызывающего это разница между «схемы с таким именем нет» и «спроси позже».

Изменяющие вызовы такой защиты не получают: `add` и `remove` в том же окне
завершаются обычным `exit({noproc, _})` от `gen_server:call`. Они и не на
горячем пути, и делает их само приложение, у которого есть `wait` с монитором; а
главное — тег фазы у `add_error()` делит ошибки надвое по содержимому схем, и
третья ветвь про доступность это деление сломала бы.

## API размещённого режима

Изменяющие вызовы дополняют загрузчик, а не заменяют его: ими добавляют схемы,
пришедшие к приложению уже в работе. Управляющий — единственный writer, и оба
идут к нему обычным `gen_server:call` со стандартным таймаутом: путь холодный, а
сериализация на одном процессе здесь и требуется.

```erlang
-spec add(atom(), [json()]) -> {ok, [uri()]} | {error, add_error()}.
-spec add_at(atom(), [{uri(), json()}]) -> {ok, [uri()]} | {error, add_error()}.
-spec remove(atom(), [uri()]) -> ok | {error, [{uri(), schema_error()}]}.

%% add_error() :: {registration, [{rid(), schema_error()}]}
%%              | {compilation,  [{uri(), schema_error()}]}.
```

Дверей у добавления две, потому что имя документа приходит из двух разных мест:
`add` берёт схемы и выводит имя из `$id`, `add_at` берёт готовые пары. Правило
именования выбирается именем функции, а не устройством аргумента, и описано
[выше](#имена). Ключом ошибки регистрации стоит `rid()`: схема, не сумевшая
назваться, зовётся `anonymous`, потому что написания у неё нет.

Ошибка называет фазу, потому что имена в двух списках значат разное. У
`registration` ключ — имя записи в том написании, с каким пришёл вызывающий: до
артефактов дело не дошло, канонического имени у отвергнутой записи может не быть
вовсе, а `name_taken` называет чужое. У `compilation` ключ — каноническое имя,
то самое, по которому артефакт лежит в таблице. Без тега вызывающему пришлось бы
различать эти случаи по форме терма и знать, в каком из них ключ годится для
`validate`, а в каком нет.

У `remove` фазы компиляции нет вовсе: удаление, прошедшее проверку ссылок, не
может сломать ни одного оставшегося артефакта — тот, кто ссылался бы на снятое
имя, отвергнут `referenced_by` раньше. Снятие артефакта тоже не подводит:
удалить отсутствующий ключ не ошибка, а потерянное владение таблицей валит
управляющего, а не возвращается вызывающему. Оттого у ошибки удаления и нет
тега: фаза одна, ключ всегда один и тот же — написание записи, — и тег, у
которого нет второго значения, вызывающему ничего не сообщил бы.

Ссылающихся управляющий ищет по `sources` выживших артефактов, тем же способом,
каким `add` находит устаревшие. Одна ссылка отвергает вызов целиком, поэтому
документ снимается только вместе со всем конусом зависимых от него; конус
вызывающий узнаёт из самой ошибки и передаёт следующим вызовом. Артефакты,
пережившие перезапуск управляющего, в проверке не участвуют и сняться не могут:
реестр о них не знает. Это та же принятая цена, что и при добавлении.

Фасад повторяет их дважды: без имени хранилища — для стандартного, с приставкой
`store_` и именем первым аргументом — для названного.

```erlang
-spec add(json() | [json()])    -> {ok, [uri()]} | {error, add_error()}.
-spec add_at(uri(), json())     -> {ok, [uri()]} | {error, add_error()}.
-spec add_at([{uri(), json()}]) -> {ok, [uri()]} | {error, add_error()}.
-spec remove([uri()])           -> ok | {error, [{uri(), schema_error()}]}.
-spec wait(timeout())           -> {ok, reference()} | {error, timeout}.
-spec validate(uri(), json(), [option()]) ->
    {ok, output()} | {error, not_found} | {error, unavailable}
                   | {error, eval_error()}.

-spec store_child_spec(atom(), [store_option()]) -> supervisor:child_spec().
-spec store_add(atom(), json() | [json()])    -> ...
-spec store_add_at(atom(), uri(), json())     -> ...
-spec store_add_at(atom(), [{uri(), json()}]) -> ...
-spec store_remove(atom(), [uri()])           -> ...
-spec store_wait(atom(), timeout())           -> ...
-spec store_validate(atom(), uri(), json(), [option()]) -> ...
```

Пары без приставки нет только у `store_child_spec/2`: стандартное хранилище
библиотека ставит в своё дерево сама, и встраивать приходится лишь собственное.

Раздельные имена выбраны не ради красоты вызова, а потому что общее имя сделало
бы `add/2` двусмысленным: `(Uri, Json)` и `(Store, Entries)` пришлось бы
различать охраной по типу первого аргумента. При раздельных именах арности
внутри каждого имени не пересекаются, и разбирать типы в рантайме не нужно. По
той же причине разведены `add` и `add_at`: первая берёт только схемы, вторая
только пары, и смешанных списков не остаётся нигде.

`validate` делает один `lookup` клиентом и зовёт `valid_json_core:validate/3`;
`not_found` означает, что имя в хранилище неизвестно, `unavailable` — что
хранилище пока не отвечает, и от `eval_error()` оба отличаются тем, что до
вычисления дело не дошло. Первым аргументом у неё идёт имя схемы, а не сама
схема: у встроенного режима на фасаде своё имя, `run_schema/3`, и различает их
имя функции, а не форма аргумента.

```erlang
-spec run_schema(json(), json(), [option() | compile_option()]) ->
    {ok, output()} | {error, schema_error()} | {error, eval_error()}.
```

`run_schema` компилирует схему в процессе вызывающего и тут же вычисляет
инстанс. Реестром ей служит `valid_json_store:temporary()`, поэтому ни
хранилища, ни запущенного приложения ей не нужно, а схема обязана быть
самодостаточной: `$ref` дотягивается только до неё самой и до встроенной
области, документы хранилищ ей не видны, и относительный `$id` разрешать не от
чего. Артефакт нигде не остаётся, и каждый вызов проходит компиляцию целиком —
дверь эта разовая, а схеме, которой пользуются не однажды, место в реестре.

Вызывающий, который уже проверил schema своим доверенным процессом, передаёт
`{trust_schema, true}` в том же списке. Опция отключает только meta-schema pass;
все остальные compile phases и validation instance остаются. При
`trust_schema = false` формат ошибки проверки схемы выбирает
`{schema_validation, flag | basic | detailed | verbose}`.

Пары с приставкой `store_` у неё нет и по нынешнему устройству быть не может:
`store()` держит документы map'ой, и снимок размещённого хранилища означал бы
копирование всего реестра из ETS на каждый вызов. Ленивый реестр поверх таблицы
менял бы саму запись `#store{}` и здесь не предполагается.

Опции обоих слоёв идут одним списком: вызывающему это опции одного вызова.
Фасад отделяет `output`, принадлежащий ядру, и передаёт остальное компилятору,
где незнакомый ключ и падает `badarg` — там же, где падал бы при прямом вызове.

`wait` стоит первой операцией того, кто собирается читать: она дожидается конца
загрузки и отдаёт монитор, по которому вызывающий узнает, что состав мог
измениться. Хранилищу без загрузчика она тоже нужна — им закрывается окно
пересборки артефактов после перезапуска хранителя.

## Артефакт на документ

Артефакт заводится на каждый документ реестра, и его имя — канонический URI этого документа. Отдельного списка публикуемых точек входа нет: множество ключей таблицы всегда совпадает с множеством канонических ключей `store()`, артефакта без документа не бывает и документа без артефакта тоже. Единственное окно, где второе временно неверно, — старт управляющего после перезапуска хранителя артефактов; оно закрывается пересборкой в `handle_continue` до первого обслуженного вызова.

Отсюда следует, что compile options принадлежат управляющему целиком, а не отдельной записи: двух артефактов одного документа под разными `default_dialect`, `assert_format` или `trust_schema` существовать не может.

Цена решения — дублирование общих целей ссылок. Файл определений, на который ссылаются десять схем, окажется в таблице одиннадцать раз: собственным артефактом и десятью копиями внутри чужих замыканий. `$schema` при этом артефакт не раздувает, потому что nodes метасхемы в `resources` не входят.

## Толстые артефакты

Одна ETS entry содержит `compiled()` вместе со всеми достигнутыми resources. Валидация делает один lookup и не склеивает зависимости. Дублирование памяти принято ради консистентности ссылок и отсутствия поколения/синхронизации на горячем пути.

Нормализованное хранение отдельных resources отвергнуто: после reload зависимости старый artifact мог бы сохранить адрес в новый несовместимый resource, и dangling ref переехал бы из compile time в runtime. Склейка на чтении также потребовала бы N lookup и протокола поколений. Толстый artifact делает согласованность свойством одной immutable entry.

`sources` задаёт invalidation. При изменении реестра управляющий:

1. выбирает артефакты, чьи `sources` пересекаются с множеством изменённых и удалённых имён, и добавляет к ним новые документы;
2. компилирует выбранное против нового `store()` с прежними опциями;
3. при полном успехе принимает новый реестр и переносит изменения в таблицы; при любой ошибке оставляет прежние реестр и артефакты.

Обратный индекс зависимостей не нужен: новый документ не может ни сломать, ни починить существующий артефакт, потому что тот, кто на него ссылается, уже держал бы его в `sources`. Пересечения с `sources`, живущими в самом артефакте, достаточно.

Ошибка возвращается списком `{compilation, [{uri(), schema_error()}]}`, где имя — каноническое имя артефакта. Артефакты компилируются независимо, поэтому сломанных бывает несколько сразу, и показать их все за один прогон полезнее, чем первый попавшийся; правило «первая ошибка прерывает» продолжает действовать внутри одной компиляции.

Реестр всегда целиком компилируем, промежуточного состояния «добавили, но пока не сходится» не существует. Из этого вытекают два правила для вызывающего: взаимно ссылающиеся документы добавляются одним вызовом, а удалить документ можно только вместе со всем транзитивным конусом зависимых от него. Второе смягчено ошибкой `{referenced_by, Uri, Refs}`, которая называет ссылающихся, так что конус узнаётся из самой ошибки.

Транзакция выполняется в порядке `put`, затем `delete`, и одинаково касается обеих таблиц: строки документов уходят в реестровую тем же коммитом, каким артефакты уходят в свою. Список `ets:insert/2` атомарен и изолирован для читателей: они видят старый либо новый набор записей. Удаление имён этой гарантией не закрыто, и выбранный порядок оставляет ровно одну наблюдаемую аномалию — снятое имя отвечает ещё некоторое время после reload. Ложного `not_found` для имени, которое остаётся жить, не возникает никогда, а несогласованного артефакта не бывает по построению, потому что запись толстая и неизменяемая.

Ленивая компиляция при lookup запрещена: deployment error должен остановить reload, а не проявиться на случайном запросе.

## ETS и процессы

Таблиц у хранилища две, обе named, `protected`, с `read_concurrency`. В первой лежат артефакты, во второй — документы реестра; в каждой есть ещё служебные строки:

| Ключ | Таблица | Значение | Кто пишет | Кто читает |
| --- | --- | --- | --- | --- |
| `Canonical` | артефактов | `compiled()` | управляющий | любой читатель |
| `ready` | артефактов | `true` | управляющий после сборки | читатель на промахе |
| `{document, Canonical}` | реестра | `#document{}` | управляющий | управляющий при старте |
| `base` | реестра | `uri()` | управляющий при старте | читатель на промахе |
| `loaded` | реестра | `true` | управляющий следом за документами загрузчика | управляющий при старте |

Служебные ключи — атомы, а имена документов — binary, поэтому столкнуться они не могут. Тегированный ключ у документа выбран затем, чтобы служебная строка не попадала в перебор документов по устройству ключа, а не по договорённости. Каждая из двух отметок лежит в той таблице, чью полноту описывает, и потому не снимается никогда: подробности — в разделе про [чтение загрузчика](#когда-загрузчик-читается). Имя регистрации отдельным ключом в таблице не заводится, хотя в самом `store()` документ лежит под обоими именами: оно есть полем документа, и обратно реестр собирает двухключевой map сам.

Истина по реестру — `store()` в состоянии управляющего; таблица ему проекция и нужна затем, чтобы пережить перезапуск. Отсюда и порядок: значение меняется первым и принимается только вместе с артефактами, а в таблицы уходит уже принятое. Обратного чтения на горячем пути нет — документы копировались бы в кучу читателя, а нужны они одному управляющему и один раз, при старте.

Процессов три, потому что таблица должна пережить падение того, кто её меняет.

**Хранитель** создаёт свою таблицу, назначает `heir` на себя и отдаёт владение по `claim/1`. Больше он не делает ничего и потому не падает: компилятор в нём не работает. Хранителей столько, сколько таблиц.

**Управляющий** держит реестр, опции и логику reload. При старте он забирает обе таблицы через `ets:give_away/3` и становится их ETS-владельцем — без этого он не смог бы писать, потому что в `protected` пишет только владелец. Когда он умирает, таблицы возвращаются хранителям по `heir` и переживают перезапуск вместе с содержимым.

Владение действует с момента самого `give_away`, а сообщение `'ETS-TRANSFER'` является только уведомлением. Поэтому ждать его не нужно: `init` управляющего делает синхронный `claim` к каждому хранителю и возвращается, а `'ETS-TRANSFER'` вычёрпывается хранителем в `handle_info`. Собственного `receive` в `init` нет.

Последовательность старта хранилища такая: супервизор поднимает хранителей, каждый создаёт свою таблицу и назначает `heir` на себя; следом поднимается управляющий, забирает обе через `claim`, поднимает реестр из его таблицы и публикует `base_uri`; в `handle_continue` он читает загрузчик, если тот задан и ещё не читался, досоздаёт недостающие артефакты и объявляет себя готовым. `base_uri` при этом берётся из опции, а не из пережившей таблицы: опция приходит через `start_link`, и супервизор перезапускает управляющего с той же самой, поэтому сравнивать её с пережившей не из чего.

Отсюда и смысл готовности: поднятое дерево означает, что процессы живы и таблицы существуют, а не что набор артефактов полон. Отметка `ready` появляется позже — концом `handle_continue`, — и до неё читатель получает `unavailable`. У хранилища без загрузчика это окно почти всегда пусто, у хранилища с ним равно времени загрузки. На горячем пути обращений ни к компилятору, ни к процессам всё равно нет: `lookup` ленивую сборку не запускает.

Три отказа разбираются так:

- **Умер управляющий.** Обе таблицы уходят к хранителям по `heir` и переживают. Новый управляющий поднимает из таблицы реестра тот же набор документов, артефакты остаются нетронутыми, пересобирать нечего, а `ready` не снималась и остаётся на месте: окна неответа у чтения не возникает вовсе.
- **Умер хранитель артефактов.** Его таблица уничтожается вместе с перезапуском управляющего, таблица реестра переживает. Документы известны, поэтому `handle_continue` компилирует их заново, а загрузчик молчит: отметка `loaded` пережила вместе со своей таблицей. Окно неответа равно времени компиляции.
- **Умер хранитель реестра.** Уничтожаются обе таблицы, и вместе с ними обе отметки. Хранилищу с загрузчиком этого достаточно: `handle_continue` читает его заново и восстанавливает набор. Хранилищу без загрузчика восстанавливать не из чего, и наполнить его заново обязано приложение — это оставшаяся полная пересборка, и сузить её нечем: источник истины исчез вместе с таблицей.

Таким этот разбор делает порядок хранителей в `rest_for_one`: реестр стоит перед артефактами, поэтому его смерть уносит обе таблицы, а смерть хранителя артефактов оставляет реестр целым. Обратный порядок давал бы пустой реестр при живых артефактах, то есть ровно то расхождение, ради устранения которого реестр и переехал в таблицу.

Сам `rest_for_one` держит не порядок старта, а связку отказов. Смерть хранителя таблицу не убивает — ею владеет управляющий, теряется лишь `heir`, — но новый хранитель упал бы на `ets:new` под занятым именем, а восстановить `heir` он не может: `ets:setopts` разрешён только владельцу. Спасает именно перезапуск управляющего следом: при его остановке таблица уходит к мёртвому heir и уничтожается, и хранитель создаёт её заново. Поэтому хранители обязаны стоять непосредственно перед управляющим в одном списке; вынести их под отдельный супервизор нельзя, не заведя вместо этого монитор и переустановку `heir` на стороне владельца.

Отказ компиляции в `handle_continue` означает не ошибку вызывающего, а расхождение внутри хранилища: эти документы уже компилировались с теми же опциями. Поэтому управляющий падает и отдаёт решение супервизору, вместо того чтобы поднимать хранилище с дырой в наборе. Отказ загрузчика разбирается там же и так же.

Ожидание готовности вынесено в `wait/2` и разобрано [вместе с загрузчиком](#готовность). Порядка сообщений оно не меняет: `handle_continue` выполняется раньше любого `call`, поэтому изменяющий вызов и без него увидит готовое хранилище. Нужно оно чтению, которое управляющего не спрашивает вовсе.

`gen_server` для `lookup` отвергнут из-за сериализации и копирования; на записи он допустим, потому что она холодная. `persistent_term` отвергнут для артефактов из-за глобальной цены обновления — на [встроенные метасхемы](#встроенные-метасхемы) это не распространяется, они пишутся один раз и не меняются.

Диспетчер с переключением между двумя таблицами остаётся возможной оптимизацией, если пауза массового `insert` станет заметна; интерфейс клиента от этого не меняется. Он добавил бы lookup текущего идентификатора таблицы и политику выбытия старой: читатель мог получить прежний идентификатор непосредственно перед подменой. Поэтому он не нужен до измеренной проблемы или требования атомарно удалять имена.
